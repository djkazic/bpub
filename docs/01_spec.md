# BPUB Specification (v5)

This document defines the BPUB v5 data format and the on-chain structures used
to embed and reveal data via Bitcoin transactions.

---

## Overview

BPUB embeds arbitrary data into Bitcoin by encoding it into **fake pubkeys**.
Each fake pubkey is a valid compressed secp256k1 public key generated by
grinding a 1-byte nonce until the x-coordinate lies on the curve.

These pubkeys are placed inside a **1-of-N multisig P2WSH script**:

```
OP_1
<data_pk_0>
...
<data_pk_M>
<control_pubkey>
OP_(M+1)
OP_CHECKMULTISIG
```

### Script layout & suffix (`padv3`)

By default, BPUB uses a **1-of-11** multisig (10 data pubkeys = 310 bytes +
1 control pubkey) with a 2-byte live suffix after `OP_CHECKMULTISIG`:

```
OP_1
<data_pk_0>
...
<data_pk_9>
<control_pubkey>
OP_11
OP_CHECKMULTISIG
OP_1
OP_EQUAL
```

Because `OP_1 OP_EQUAL` simply verifies that `OP_CHECKMULTISIG` returned `1`,
the reveal witness carries **no extra padding items**—just the standard
1-of-N witness stack (newest last):

```
<CHECKMULTISIG dummy = ""> <signature> <redeemScript>
```

Keeping at most 10 data pubkeys per script stays within the 10-unproven-key
per-input allowance under verified-key datacarrier recounting (Knots
`v29.5.1+`, `knots#470`), while the trailing `OP_1 OP_EQUAL` avoids matching
bare `OP_CHECKMULTISIG`-terminated multisig heuristics without introducing a
dead branch or witness malleability.

**`padv2` / `padv1` suffixes (legacy).** Earlier padded variants used 1-of-15
multisigs with 13 `OP_CHECKSIG` padding opcodes in an `OP_NOTIF` branch
(`OP_SIZE <64> OP_EQUAL OP_NOTIF` in `padv2`, `OP_1 OP_NOTIF` in `padv1`) and
13 deterministic 64-byte DER-shaped padding items (`sha512("BPUB-PAD-ITEM" ||
script || index)`) ahead of `[dummy, signature, script]`. They are no longer
built by default, but the parser, indexer, and `signreveal` still recognize
and sign them for already-funded outputs. Use `--legacy-scripts` for UTXOs
funded with legacy suffix-free 1-of-15 scripts.

### Funding output values

A `padv3` reveal input measures ~155 vB on average (the fee estimator uses
175 vB for headroom). `txbuild`/`fundpsbt` size each BPUB data output by
default to cover its share of the reveal at the assumed reveal feerate
(`--reveal-feerate`, defaulting to the funding feerate):

```
value_i = max(547, 175 * reveal_feerate + ceil((134 * reveal_feerate + 546) / n))
```

where `134` vB is the reveal's fixed overhead (base + one output) and `n`
the number of data outputs. The `+ 546 / n` share guarantees the reveal's
change output clears the dust floor, and flooring at `547` sats ensures no
P2WSH output sits at or below `546` sats while keeping upfront capital
linear (`O(n)`, at most `1 sat` per output over `546`) rather than
quadratic. `--bpub-value` overrides the sizing with an exact per-output
value.

Version 5 introduces **mandatory ownership**, using a separate P2WSH output:
```
<BPUB_ID>
OP_DROP
OP_DUP
OP_HASH160
<owner_h160>
OP_EQUALVERIFY
OP_CHECKSIG
```

## BPUB v5 Stream Format

The BPUB v5 stream encodes metadata and content, optionally using raw DEFLATE +
XOR obfuscation.
```
[0:4]   stream_len (uint32, BE)
[4]     version = 5
[5]     flags
[6:14]  size_uncompressed (uint64, BE)
[14:46] sha256(uncompressed) (32 bytes)
[46:48] meta_len (uint16, BE)
[48:??] meta_blob_enc (XOR(raw_deflate(JSON)), optional)
[..]    content_enc (XOR(deflated data) or XOR(raw data))
```

### Flags

| Bit | Meaning                          |
|-----|----------------------------------|
| 0   | Content is raw-deflate-compressed before XOR |
| 1   | Metadata is present              |

---

## Metadata Format (JSON)

If metadata exists, it's encoded as raw-deflate(JSON) and XOR-obfuscated.

Example metadata:

```json
{
  "mime": "image/jpeg",
  "filename": "cat.jpg",
  "bpub_id": "c2b7...9af3"
}
```

## BPUB_ID
```
bpub_id = sha256("BPUB5" || sha256(data) || size_be_8)
```

This value identifies the inscription and is committed to in the ownership
redeem script.

## Ownership Redeem Script

The owner output commits to the BPUB_ID and behaves like a P2WPKH script,
but wrapped in P2WSH:
```
<BPUB_ID>
OP_DROP
OP_DUP
OP_HASH160
<owner_h160>
OP_EQUALVERIFY
OP_CHECKSIG
```

This ensures that ownership of the BPUB can be transferred without revealing
the data.

## Reveal Transaction
To reveal the data, each multisig output must be spent. The script is recovered
from the witness, data pubkeys are extracted, decoded, and reassembled into the
BPUB stream. Once reconstructed, the original file can be recovered.

## Multipart Files (v1)

A single `padv3` reveal transaction must stay within the 400,000 WU standardness
limit (~195 KiB of encoded BPUB stream across 630 1-of-11 scripts). Files larger
than a single reveal transaction are split across **part** inscriptions and tied
together by a **manifest** inscription whose txid acts as the file's canonical
link. Both are ordinary BPUB v5 inscriptions, so the underlying stream format is
unchanged and wire-compatible with `@bitfiles/bpub`.

- **Whole-file compression:** The original file is optionally raw-DEFLATE
  compressed once (`"deflate-raw"` when smaller, otherwise `"none"`), then
  sliced so each part's v5 stream fits within the target stream budget.
- **Part inscriptions:** Inscribed as BPUB v5 with
  `mime = "application/vnd.bpub.part"` and `compress = false` (no per-part
  stream compression). Indexers store parts privately and hide them from
  top-level gallery listings.
- **Manifest inscription:** Inscribed as BPUB v5 with
  `mime = "application/vnd.bpub.manifest+json"` and `compress = true`, carrying
  canonical UTF-8 JSON:

```json
{
  "bpub_manifest": 1,
  "mime": "image/png",
  "filename": "large.png",
  "size": 524288,
  "sha256": "<64-hex sha256 of the reassembled uncompressed file>",
  "compression": "deflate-raw",
  "parts": ["<part0_txid>", "<part1_txid>", "<part2_txid>"]
}
```

- **Canonical `bpub_id`:** Reassembled multipart files derive their v5
  `bpub_id = sha256("BPUB5" || sha256 || size_be_8)` from the manifest's
  `sha256` and `size`, producing the exact same `bpub_id` as a single-tx v5
  inscription.
- **Verification:** Readers join part contents in manifest order, inflate with a
  hard decompression bound when `compression == "deflate-raw"`, and require an
  exact match on both `size` and `sha256`.

## Legacy Versions
* v3.5: TLV header with "BPUB" magic and cleartext metadata.

* v4: Same binary layout as v5, but no ownership.

* v5: (current) — Adds bpub_id, ownership, and optional metadata fields.
